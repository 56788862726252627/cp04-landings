## Cómo mergear cada una (mecánica recomendada)

Para cada PR, en orden:

1. `gh pr checks <N>` — confirmar que no hay checks fallando (si hay CI configurado).
2. `gh pr merge <N> --merge` (merge normal, **no** squash — cada commit ya es atómico y descriptivo; squashear perdería la trazabilidad prompt-a-prompt) — **o el método que prefiera el equipo**, pero nunca `--rebase` en esta cadena (podría reescribir SHAs de los que dependen las PR siguientes antes de que GitHub actualice sus bases).
3. Tras cada merge, GitHub re-apunta automáticamente la base de la siguiente PR de la cadena a `main` (o a la rama objetivo) — **verificar con `gh pr view <N+1>` que `baseRefName` se actualizó** antes de continuar.
4. Ejecutar `npm test && npm run lint && npm run build` sobre `main` tras cada merge (no solo al final) — para aislar inmediatamente cuál PR concreta introduce un problema, si aparece alguno.
5. Repetir para la siguiente PR.

## Riesgos de conflicto

GitHub reporta las 14 PR como `MERGEABLE` hoy (confirmado en la Fase 0 de este prompt), lo que significa que, en el estado actual, ninguna tiene conflictos de merge detectados automáticamente. Sin embargo:

- **Riesgo real, no de Git sino de contenido:** las PR #54-#57 tocan el sidebar/Perfil varias veces de forma incremental (bug real → fix → refinamiento). Mergearlas todas en orden es seguro porque cada una parte del estado de la anterior, pero si en algún momento se mergea solo un subconjunto (p. ej. solo hasta #55) y se abandona el resto, el sidebar quedaría en un estado intermedio ya superado — **no mergear parcialmente esta sub-cadena**.
- **Riesgo de ventana temporal:** si `main` recibe commits directos entre el momento de este plan y el momento real del merge (alguien más trabajando en main), las bases de #52 y sucesivas podrían necesitar un rebase manual — comprobar `git log main` inmediatamente antes de empezar.
- **Sin conflictos de contenido esperados** entre PR no adyacentes: cada prompt trabajó en archivos bien delimitados (mayormente `App.jsx` de forma secuencial + un archivo de test nuevo por prompt + un documento nuevo por prompt) — el patrón de "un test file nuevo, un doc nuevo, ediciones puntuales a App.jsx" no genera colisiones de línea entre PR no adyacentes.

## Estrategia de rollback

- **Revertir una sola PR ya mergeada:** `git revert <commit>` en `main`, en orden inverso empezando por la PR más reciente que dependa de ella (si se revierte #58 sin revertir antes #59-#65, `git revert` puede fallar por conflicto — revertir siempre de la más nueva a la más vieja).
- **Revertir todo el bloque:** `git revert` de los 14 commits en orden inverso (#65 → #52), o `git reset` a un tag/commit anterior al primer merge **únicamente si nadie más ha construido sobre `main` desde entonces** (y solo con autorización expresa — regla explícita: no `reset --hard` sin permiso).
- Ninguna PR de esta cadena borra datos de usuario reales ni migra esquemas — el rollback de código es seguro sin pasos adicionales de datos.
