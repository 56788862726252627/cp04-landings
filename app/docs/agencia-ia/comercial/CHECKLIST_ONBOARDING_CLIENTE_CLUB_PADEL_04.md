# Checklist de Onboarding de Cliente — Club Pádel 04 / Agencia IA

**Uso**: documento de uso interno. Se activa en cuanto un ayuntamiento, polideportivo o club deportivo muestra interés real, para pasar de "cliente interesado" a "implantación preparada" sin improvisar en el camino.

---

## 1. Objetivo del checklist

Este checklist sirve para recopilar de forma ordenada toda la información necesaria antes de adaptar e implantar el sistema en un nuevo cliente. Evita que la fase posterior a la primera reunión o contacto dependa de la memoria o de preguntas sueltas — cada punto pendiente aquí es un punto que, si no se resuelve, retrasará la demo, la propuesta o la implantación.

---

## 2. Datos básicos del cliente

- [ ] Nombre del municipio/club.
- [ ] Tipo de entidad (ayuntamiento, polideportivo municipal, club privado, gimnasio, otro).
- [ ] Persona responsable.
- [ ] Cargo de la persona responsable.
- [ ] Teléfono de contacto.
- [ ] Email de contacto.
- [ ] Web oficial.
- [ ] Dirección.
- [ ] Fecha de primer contacto.
- [ ] Estado comercial (sin contactar / contactado / demo agendada / propuesta enviada / en negociación / cerrado / descartado).

---

## 3. Datos de la instalación deportiva

- [ ] Nombre de la instalación.
- [ ] Dirección de la instalación.
- [ ] Número de pistas.
- [ ] Tipos de pista (pádel, tenis, multideporte, otras).
- [ ] Deportes disponibles.
- [ ] Horarios habituales.
- [ ] Días de apertura.
- [ ] Normas actuales de uso de la instalación.
- [ ] Responsable operativo de la instalación (quien la gestiona en el día a día).

---

## 4. Sistema actual de reservas

- [ ] Cómo reservan actualmente los usuarios (teléfono, WhatsApp, presencial, web, app, papel, otro).
- [ ] Quién gestiona las reservas hoy.
- [ ] Problemas principales detectados en la gestión actual.
- [ ] Volumen aproximado de reservas (diario/semanal, estimado por el cliente).
- [ ] Horas punta de uso.
- [ ] Incidencias frecuentes (dobles reservas, errores, quejas habituales).

---

## 5. Reglas de reserva

- [ ] Duración estándar de cada reserva.
- [ ] Antelación permitida para reservar.
- [ ] Política de cancelaciones.
- [ ] Límites por usuario (nº de reservas simultáneas, por semana, etc.).
- [ ] Precios actuales, si existen.
- [ ] Bonos o abonos existentes.
- [ ] Si las reservas son gratuitas o de pago.
- [ ] Si hay diferencia entre socios/no socios (o vecinos/no vecinos).
- [ ] Excepciones o casos especiales a tener en cuenta.

---

## 6. Usuarios y roles necesarios

Confirmar con el cliente qué se espera de cada rol antes de configurarlo:

- [ ] **Jugador/vecino**: qué puede ver y hacer exactamente.
- [ ] **Recepción/staff**: qué nivel de gestión diaria necesita.
- [ ] **Administrador**: quién tendrá este nivel y qué control necesita.
- [ ] **Soporte**: si se necesita un perfil de soporte interno y quién lo ocupará.
- [ ] **Responsables municipales**: quién debe tener visibilidad sin necesariamente gestionar el día a día.

---

## 7. Personalización visual

- [ ] Nombre público que tendrá el sistema para este cliente.
- [ ] Logo.
- [ ] Colores corporativos/municipales.
- [ ] Imágenes representativas de la instalación.
- [ ] Textos principales (bienvenida, normas, avisos).
- [ ] Información de contacto a mostrar.
- [ ] Normas visibles para el usuario final.
- [ ] Enlaces útiles (web municipal, redes sociales, otros).

---

## 8. Módulos incluidos en primera fase

- [ ] Login.
- [ ] Reservas.
- [ ] Perfil de usuario.
- [ ] Ranking.
- [ ] Torneos.
- [ ] Panel de gestión.
- [ ] Avisos básicos.
- [ ] Soporte durante la puesta en marcha.
- [ ] Manual de uso.
- [ ] Demo previa antes de la puesta en marcha.

---

## 9. Módulos fuera de primera fase

Dejar claro por escrito, antes de firmar nada, que **no** están incluidos salvo presupuesto aparte:

- Pagos online reales.
- Mensajería empresarial avanzada para avisos automáticos.
- Integraciones externas complejas con otros sistemas del cliente.
- Hardware de cualquier tipo.
- Control físico de acceso a las instalaciones.
- Desarrollos ilimitados de nuevas funcionalidades.
- Campañas publicitarias o de comunicación.
- Cualquier funcionalidad no pactada expresamente por escrito.

---

## 10. Datos necesarios para preparar la demo personalizada

- [ ] Nombre del municipio/club.
- [ ] Nombre de la instalación.
- [ ] Pistas de ejemplo (reales o ficticias si aún no se han confirmado los datos definitivos).
- [ ] Horarios reales o ficticios para la demo.
- [ ] Normas a reflejar.
- [ ] Logo (si ya está disponible).
- [ ] Colores (si ya están definidos).
- [ ] Usuario de prueba preparado.
- [ ] Flujo concreto que se quiere mostrar en la demo (reserva, torneo, gestión, etc.).

---

## 11. Checklist técnico interno (sin revelar proveedores)

Revisión interna antes de cualquier demo o entrega, en lenguaje comercial/operativo:

- [ ] Revisar que la aplicación carga y funciona correctamente.
- [ ] Revisar que los roles están configurados según lo acordado con el cliente.
- [ ] Revisar los textos públicos (sin errores, sin datos de otro cliente).
- [ ] Revisar que una reserva de demostración funciona de principio a fin.
- [ ] Revisar el módulo de torneos si se va a mostrar.
- [ ] Revisar el panel de gestión antes de enseñarlo.
- [ ] Revisar que no se muestra ningún dato privado de otro cliente (privacidad pública).
- [ ] Revisar que la documentación de este cliente está completa antes de avanzar a la siguiente fase.

---

## 12. Checklist comercial antes de enviar contrato

- [ ] Precio confirmado por escrito (setup + mantenimiento).
- [ ] Alcance confirmado (qué incluye y qué no incluye).
- [ ] Mantenimiento mensual confirmado (qué cubre exactamente).
- [ ] Fase piloto confirmada (si aplica, y sus condiciones).
- [ ] Responsable de la decisión final identificado.
- [ ] Fecha objetivo de puesta en marcha.
- [ ] Condiciones de pago acordadas.
- [ ] Fecha de la siguiente reunión ya fijada.

---

## 13. Riesgos a detectar antes de aceptar el cliente

- Expectativas irreales sobre lo que el sistema puede hacer desde el primer día.
- Demasiadas personalizaciones solicitadas antes incluso de cerrar el piloto.
- Falta de un responsable interno claro en el lado del cliente.
- Falta de datos básicos que impide avanzar (instalación, horarios, normas).
- Urgencia extrema que no da margen para una implantación cuidada.
- Presupuesto insuficiente respecto a lo que se está pidiendo.
- Solicitud de cambios fuera del alcance ya acordado.
- Necesidad real de integraciones no incluidas en esta fase (pagos, mensajería avanzada, sistemas externos).

Si aparecen varios de estos riesgos a la vez, conviene replantear el alcance o el precio antes de seguir adelante, no después de empezar la implantación.

## 15. Próximo paso tras completar el checklist

1. Preparar la propuesta comercial final adaptada a este cliente.
2. Preparar la demo personalizada con los datos recogidos en el punto 10.
3. Validar el precio final con el cliente antes de redactar el contrato/presupuesto.
4. Enviar el contrato o presupuesto formal.
5. Planificar la implantación siguiendo el proceso ya definido (reunión inicial → adaptación → demo interna → ajustes → puesta en marcha → mantenimiento).
